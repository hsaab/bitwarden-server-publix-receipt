# Candidate B: net8.0 to net10.0 pin upgrade

## Approach

Move the central pin, the ten per-project overrides, and every package that cannot restore on net10.0 in one change. Those edits only produce a tree that restores and compiles when they land together. `Directory.Build.props` and the ten overriding projects switch to `net10.0`, `global.json` switches to SDK `10.0.100` with the existing `rollForward` of `latestFeature`, and the 8.0 Microsoft.EntityFrameworkCore, Microsoft.AspNetCore, Microsoft.Extensions, and System.Text.Json packages move to exact 10.0 patches, with Npgsql and Pomelo moved to stable releases that depend on EF Core 10. The six `new X509Certificate2(...)` sites move to `X509CertificateLoader` in that same change, because warnings are errors and that API is not on net8.0.

## Why this over the obvious alternative

The obvious alternative is a stack of slices: SDK first, then package bumps while the repo still targets net8.0, then the TFM. That stack never has a green middle commit. The current 8.0 framework packages do not ship net10.0 assets, and the EF Core 10 and ASP.NET Core 10 packages do not ship net8.0 assets, so either order fails restore with NU1202. A warning-only first slice fails for the same reason: `X509CertificateLoader` is not on net8.0, and a repo-wide SYSLIB0057 suppression would hide the break the new TFM introduces. Adding `Directory.Packages.props` is a second alternative, and it is the wrong shape for this repo, which pins every version on the `PackageReference` and has no central package file.

## Risks

- Pomelo or Npgsql may have no stable package that depends on EF Core 10. Early warning: `dotnet restore` fails on `Infrastructure.EntityFramework.csproj` with NU1102 or NU1202 naming that provider.
- `Bitwarden.Server.Sdk` 1.5.1 may not load on the 10.0 SDK. Early warning: restore fails on a host project whose Sdk is `Bitwarden.Server.Sdk`, before any of our C# compiles.
- The net10 compiler may emit warnings-as-errors beyond the six SYSLIB0057 sites. Early warning: the build lists a different warning code, and the new sites push the diff toward the 500-line cap.
- EF Core 10 or ASP.NET Core 10 may remove members this pin calls. Early warning: CS0117 or CS1501 in `Infrastructure.EntityFramework` or in auth and startup code, naming an EF or authentication member.
- `Microsoft.Build.Sql` 1.0.0 may fail while restoring the solution on the new SDK. Early warning: the error names `Microsoft.Build.Sql` or `Sql.sqlproj` and does not name a `PackageReference`. Bump only that msbuild-sdk, inside this slice, when that error appears.
- xunit 2.6.6 or `Microsoft.NET.Test.Sdk` 18.0.1 may refuse a net10.0 test project. Early warning: `Core.Test` restores and compiles, then `dotnet test` fails in the runner before any test result. Bump only the package the runner names.
- A plain `dotnet build bitwarden-server.sln` can still fail after this slice. Early warning: the log mentions `cargo build --release` or `Sql.sqlproj`.

## Least sure about

Whether the acceptance build should be a plain `dotnet build bitwarden-server.sln` instead of restore of that solution plus the four project builds above. I am keeping the SQL project and `RustSdk` out of the compile gate because CI deletes `src/Sql/Sql.sqlproj` before tests and `Core.Test` does not need cargo. What would change my mind: a solution restore, or a one-line `Microsoft.Build.Sql` bump, makes `dotnet build bitwarden-server.sln` succeed on this machine without cargo. If the only remaining failure is a missing `cargo` binary, I would still leave `RustSdk` out of the gate rather than install Rust or edit its PreBuild.
